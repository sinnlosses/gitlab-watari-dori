## 1. 概要・目的

`develop → staging → production` のような多段リリースフローを持つチームでは、同じ内容の
マージリクエスト（MR）を毎回手で作る手間が繰り返し発生する。gitlab-watari-dori は
**GitLab CI のスケジュールパイプラインから定期実行され、設定されたブランチペアを巡回して、
差分があり MR がまだ無いときだけ MR を作成する** CLI ツールである。

「渡り鳥が季節ごとに決まった経路を辿る」ように、**毎回同じ経路（ブランチペア）を、状態を
持たずに一巡する**のが設計の中心。前回の実行結果を保存せず、毎回 GitLab の現在の状態だけを
見て判断する。

## 2. スコープ

### 2.1 対象とすること

- 設定ファイル（`config/*.yaml`）に定義された複数プロジェクト × 複数ブランチペアの巡回
- ブランチ存在確認 → 差分コミット確認 → オープン MR 確認の 3 段階チェック
- 条件を満たすペアへの MR 作成（タイトルは自動生成）
- 一時的な API エラー（429 / 502 / 503 / 504）の指数バックオフリトライ
- 構造化 JSON ログの標準出力への書き出し
- 起動時の設定バリデーションと環境変数バリデーション

### 2.2 対象外とすること（スコープ外）

| 対象外                          | 理由                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------- |
| MR のマージ・承認               | 人間のレビューを前提とする。自動化するとリリース判断を機械に委ねることになる |
| MR の説明文・ラベル・アサイニー | チームごとに要求が違う。必要になった時点で設定項目として追加する             |
| コンフリクト解消                | 内容の判断が必要で自動化できない                                             |
| GitHub / Bitbucket 対応         | GitLab API 専用。他ホスティングは現時点で要求が無い                          |
| 実行結果の永続化・差分の追跡    | 毎回 GitLab の現在状態だけで判断する（状態を持たない）                       |
| 通知（Slack / メール）          | CI のパイプライン失敗通知で代替できる                                        |

### 2.3 想定利用者

チーム内限定。設定ファイルを書き、GitLab CI のスケジュールを設定できる開発者を想定する。

## 3. 機能要件

### 3.1 MR 作成の判定順序

1 ブランチペアにつき、**必ずこの順**で判定する（`src/main.ts` の `createMrIfNeeded`）。

| 順  | 判定                         | 満たさないとき           | 理由                                                     |
| --- | ---------------------------- | ------------------------ | -------------------------------------------------------- |
| 1   | source / target が実在する   | `ERROR`                  | 設定ミスとみなす。黙って無視すると設定の誤りに気づけない |
| 2   | source → target に差分がある | `SKIPPED`（`no_diff`）   | 差分が無い MR は作れない                                 |
| 3   | 同じペアのオープン MR が無い | `SKIPPED`（`mr_exists`） | 重複作成を防ぐ                                           |
| 4   | `DRY_RUN` でない             | `SKIPPED`（`dry_run`）   | 事前確認モード                                           |

すべて満たしたときだけ MR を作成し `CREATED` を返す。

**この順序は入れ替えない**: 判定が進むほど API 呼び出しが増えるため、前段で落ちるペアは
後段の呼び出しを行わない。`ERROR` を返すのは 1 のブランチ不在だけで、2〜4 はすべて
`SKIPPED`（`reason` で区別する）。

### 3.2 対象の設定

- 対象は `config/` ディレクトリ内の `.yaml` / `.yml` を**アルファベット順**に読み込んで結合する
- `CONFIG_PATH` で単一ファイル指定もできる。ただし**作業ディレクトリ外のパスは拒否する**
- 起動時に Zod でスキーマを検証する。`source` / `target` の空文字と、`source === target` は
  エラーで即時終了する

### 3.3 並列実行とスキップ

- `CONCURRENCY_LIMIT`（既定 5、1〜20 の整数）で同時実行数を制御する
- `SKIP_PROJECT_IDS`（カンマ区切り）に含まれるプロジェクトは処理前に除外する。
  数値に変換できない値・空セグメントは**黙って捨てる**（緊急時に手で書く値なので、
  書式ミスで全体を止めない）

### 3.4 ドライラン

`DRY_RUN=true` のとき、**MR 作成だけ**をスキップする。ブランチ確認・差分確認・既存 MR 確認は
実行するため、「どのペアで MR が作られるか」を API への書き込みなしで事前確認できる。

## 4. 非機能要件

### 4.1 実行環境

- Node.js 22.x / pnpm 11.x、TypeScript（ESM）
- 常駐しない。1 回の実行で全ペアを処理して終了する
- 実行主体は GitLab CI のスケジュールパイプライン（`create-merge-requests` ジョブ）

### 4.2 エラー処理

| ケース                                 | 挙動                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| 401 / 5xx / ネットワーク障害           | `FatalError` を投げて即時 `exit(1)`。残りのキューも破棄する |
| 429 / 502 / 503 / 504                  | 指数バックオフで最大 3 回リトライ（1s → 2s）                |
| ブランチ不在・403・その他の API エラー | 該当ペアを `ERROR` として記録し、他のペアの処理は続ける     |

`ERROR` が 1 件以上あれば `PARTIAL_FAILURE` として `exit(1)` する（パイプラインを失敗させて
人間に気づかせる）。

**401 を fatal、403 を継続とする理由**: トークンは 1 本を全プロジェクトで共有するため、
401（認証失敗）は全件に影響する。403（権限不足）は特定プロジェクトだけの問題なので、
他のプロジェクトを巻き込まない。

### 4.3 ログ

- すべて JSON 1 行で標準出力・標準エラーに書く。CI ログからそのまま収集・解析できること
- `run_start` → 各ペアの結果 → `summary` → `run_end` の順に出す
- `token` / `password` / `secret` などのキーは値を `[REDACTED]` に置き換える

### 4.4 セキュリティ

- アクセストークンは環境変数のみで受け取る。設定ファイルには書かない
- CI では `ACCESS_TOKEN` を **Masked: ON / Protected: ON** で登録する
- `CONFIG_PATH` のパストラバーサルを拒否する
