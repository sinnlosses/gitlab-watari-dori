# アーキテクチャ詳細

ディレクトリ構成の一覧は [`README.md`](../README.md)「プロジェクト構成」が正典。ここには
**なぜその形なのか**と、**新しいコードをどこに置くか**を書く。

## 節の索引

| 節                     | 何が書いてあるか                                       |
| ---------------------- | ------------------------------------------------------ |
| 全体の流れ             | エントリポイントから MR 作成までの呼び出し順           |
| 各ディレクトリの責務   | `lib/` と `utils/` の境界、`types.ts` の役割           |
| 新しいコードを置く場所 | 置き場の早見表と、1 ファイルにまとめるか分けるかの判断 |
| 設計判断               | 今の形になっている理由（変えるときに読む）             |
| 既知の制約・注意点     | 直感に反する挙動                                       |

## 全体の流れ

```
index.ts            run() を呼び、戻り値と例外を終了コードに変換するだけ
  └─ main.ts run()          全体を timed() で包み、run_start / summary / run_end を出す
       └─ process()          設定読み込み・スキップ除外・p-limit で並列化・件数集約
            └─ createMrIfNeeded()   1 ブランチペア分の判定と MR 作成
                 └─ lib/gitlab.ts    GitLab API 呼び出し（すべて withRetry で包む）
```

**原則**: この 4 段より下に段を増やさない。判定のロジックは `createMrIfNeeded` に集約し、
`lib/gitlab.ts` は「API を 1 回叩いて素直な値を返す」だけに保つ。

## 各ディレクトリの責務

### `src/lib/` — 特定の外部システム・ファイル形式に依存する処理

| ファイル    | 責務                                                                 |
| ----------- | -------------------------------------------------------------------- |
| `gitlab.ts` | `@gitbeaker/rest` の呼び出し。gitbeaker の型を知ってよいのはここだけ |
| `config.ts` | YAML の読み込みと Zod による検証。`js-yaml` を知ってよいのはここだけ |
| `env.ts`    | 環境変数の読み取りと検証。`process.env` に触れてよいのはここだけ     |

### `src/utils/` — ドメイン知識を一切持たない汎用処理

| ファイル    | 責務                                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `errors.ts` | `FatalError`（`httpStatus` と `cause` を保持する）                                                                           |
| `http.ts`   | HTTP ステータスの抽出と分類（`extractHttpStatus` / `isNotFoundError` / `isFatalStatus` / `isFatalError` / `toErrorMessage`） |
| `retry.ts`  | `withRetry`。429 / 502 / 503 / 504 を指数バックオフで再試行                                                                  |
| `logger.ts` | JSON 1 行のロガー。機微なキーを `[REDACTED]` に置き換える                                                                    |
| `timer.ts`  | `timed`。戻り値と経過時間を組にして返す                                                                                      |

**`utils/http.ts` だけは例外的に gitbeaker のエラー構造（`Error → cause.response.status`）を
知っている。** ファイル冒頭にその旨のコメントがあり、gitbeaker のメジャーバージョンアップ時に
最初に見る場所になっている。

### `src/types.ts` — このツールの語彙

ブランド型（`ProjectId` / `ProjectName` / `BranchName` / `GitLabUrl`）とその factory 関数、
および設定・結果の型（`BranchPair` / `RepoConfig` / `Config` / `MrCreationResult` /
`RunResult`）を置く。**`src/main.ts` に `type` を定義しない**（規約。理由は
[`coding-standards.md`](./coding-standards.md)「型の置き場所」）。

## 新しいコードを置く場所

| 書こうとしているもの                                 | 置き場                |
| ---------------------------------------------------- | --------------------- |
| 外部システム・ファイル形式・ライブラリに依存する処理 | `src/lib/<対象>.ts`   |
| どのプロジェクトでも通用する汎用処理                 | `src/utils/<概念>.ts` |
| 型・ブランド型とその factory                         | `src/types.ts`        |
| 判定のロジック（何を作るか決める）                   | `src/main.ts`         |
| CI・開発用スクリプトからしか呼ばれないコード         | `scripts/<用途>/`     |

**「複数箇所から呼ばれる」は `utils/` に置く理由にならない。** 判断軸は依存の向きだけで、
利用箇所の数では決めない。

**`helpers.ts` / `utils.ts` / `common.ts` のような、置き場所を名前にしたファイルを
`src/` に作らない**（`test/helpers.ts` はテスト用フィクスチャなので対象外）。
ファイル名が概念になっていないなら、既存のどれかに入る場所があるということ。

## 設計判断

### `FatalError` を投げたら残りのキューを捨てる

`process()` は各タスクを `try`/`catch` で包み、`FatalError` を見つけた瞬間に
`limit.clearQueue()` を呼ぶ。`p-limit` は各タスクの完了後に次のタスクを起動するため、
`Promise.all` の `catch` 側では次が始まるのに間に合わない。**401 やサーバー障害のときに
残り全件へ無駄なリクエストを投げないため**にこの位置で割り込んでいる。

### `createMrIfNeeded` の中だけで `try`/`catch` する

エラーを `ERROR` という値に変換するのはこの関数の責務で、呼び出し側（`process()`）は
`FatalError` の検出以外はしない。`lib/gitlab.ts` は `isNotFoundError` の判定を除いて
例外をそのまま投げ上げる。

### ブランド型の生成は factory 関数に封じ込める

`as` キャストが出てよいのは `src/types.ts` の `toProjectId` などの中だけ。呼び出し側は
`as` を書かない。`config.ts` の Zod スキーマも `.transform(toBranchName)` の形で factory を
通しており、検証を抜けた値だけがブランド型になる。

### `env.ts` はモジュールのトップレベルで評価する

`GITLAB_URL` などは `import` した瞬間に読み取り・検証される。**環境変数の不備は起動直後に
落ちるべき**で、処理の途中で初めて気づくより早い。その代わり、テストで環境変数を差し替える
ときは `vi.mock` でモジュールごと置き換える必要がある。

### グループ = 設定ファイル 1 つ、単一トークンへのフォールバックは作らない

トークンを割り当てる単位（`ConfigGroup`）を「設定ファイル 1 つ」にしているのは、
`config/` がもともと人や運用の都合でリポジトリ群ごとにファイルを分ける前提だったから。
新しいグルーピングの概念を足さずに、既存のファイル境界をそのままトークンの境界として
再利用している。`loadConfigDir` が `repositories` を連結せずファイル単位のまとまりを
保っているのはこのため。

`accessTokenEnv` を必須にし、未設定時に単一の `ACCESS_TOKEN` へフォールバックする
経路を作らなかったのは、**書き漏らした設定ファイルが黙ってより広い権限のトークンへ
流れる形を残さないため**。フォールバックがあると、スコープを絞った Group/Project
Access Token を使うつもりで書いた設定ファイルが、書き忘れ 1 つで別のトークン（多くは
より広い権限を持つ）に流れてしまう。`assertAccessTokensPresent` が起動時に全グループ
ぶんの環境変数をまとめて検証し、1 つでも欠けていれば MR を 1 件も作らずに落ちるのは、
この「絞ったトークンを絞ったまま使わせる」方針を実行時にも徹底するため。

### アクセストークンだけはトップレベルの `const` にしない

トークンが入っている環境変数の名前は設定ファイルの `accessTokenEnv` 由来で、実行時にしか
分からない。そのため `env.ts` は名前を受け取る関数（`loadAccessToken` /
`assertAccessTokensPresent`）を提供し、`process()` は設定を読んだ直後に
`assertAccessTokensPresent` で**全グループぶんをまとめて**検証する。1 つでも未設定なら
MR を 1 件も作らずに落ちる。足りない名前を 1 つずつ投げないのは、設定漏れを何度も
実行して見つけることにならないようにするため。

### クライアントはグループごと、`pLimit` は 1 つ

トークンがグループ（設定ファイル 1 つ）単位なので `createClient` もグループごとに呼ぶ。
一方 `pLimit` は `process()` に 1 つだけ作って全グループで共有する。グループごとに作ると
同時実行数が `CONCURRENCY_LIMIT × グループ数`まで膨らんでしまう。

### `withRetry` は `lib/gitlab.ts` の各関数の中で呼ぶ

呼び出し側がリトライを意識しなくて済むよう、API を叩く関数がそれぞれ自分で包む。
**リトライ対象は HTTP ステータスだけ**（429 / 502 / 503 / 504）で、ネットワーク障害は
リトライせず fatal として扱う。

### `hasDiff` は target を base に置く

`gitlab.Repositories.compare(projectId, target, source)` の順で呼び、
**source にあって target に無いコミット**を数える。引数の順を入れ替えると常に 0 件になる。

## 既知の制約・注意点

### `CONCURRENCY_LIMIT` は API への同時接続数の上限ではない

制御しているのは**ブランチペア単位のタスク数**であり、1 タスクの中で `branchExists` を
source / target の 2 本ぶん `Promise.all` で同時に投げている。実際の同時リクエスト数は
最大でこの値の 2 倍になりうる。

### `SKIP_PROJECT_IDS` の書式ミスは黙って無視される

`parseSkipProjectIds` は数値に変換できない値・0 以下・非整数を捨てる。タイプミスがあっても
エラーにならず、そのプロジェクトはスキップされずに処理される。`skip_projects` イベントの
ログに実際にスキップされた ID が出るので、そこで確認する。

### `DRY_RUN` は読み取り API を止めない

ブランチ確認・差分確認・MR 一覧取得は実行される。レート制限に当たる可能性は本番実行と
変わらない。

### `FatalError` 発生時、実行中のタスクは途中で打ち切られる

`limit.clearQueue()` が捨てるのは**まだ始まっていないタスク**だけで、すでに走っている
最大 `CONCURRENCY_LIMIT` 件は `Promise.all` の reject → `process.exit(1)` によって
途中で止まる。ただし**送信済みのリクエストは GitLab 側で処理される**ため、`CREATED` の
ログが出ていない MR が作られている可能性がある。fatal 終了のあとは GitLab 上の MR を
目で確認する。
